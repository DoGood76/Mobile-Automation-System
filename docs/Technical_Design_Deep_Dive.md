# Mobile Automation Testing System

## 1. Overview

This document outlines the **technical design** of a Mobile Automation Testing System built to support end-to-end mobile test execution, triggered manually or programmatically, within an on-premises infrastructure.

The system is modular, message-driven, and supports scalable orchestration of test execution on physical and virtual devices. Key interfaces are standardized to ensure compatibility with future trigger mechanisms and tool integrations.

## 2. Component Architecture

### 2.1 Trigger Listener

* **Role**: Captures test initiation requests from Jenkins, Bitbucket, Xray, or schedulers.
* **Function**: Converts requests into standardized trigger messages and sends them to the message queue.
* **Example**: An Xray test execution triggers Jenkins via API; Jenkins notifies the listener, which emits a trigger event.

### 2.2 Trigger Router

* **Role**: Validates, enriches, and routes messages.
* **Function**: Adds metadata (branch, tags, environment, test suite) and sends to Test Planner.
* **Example**: Maps project metadata and device filters to route test plans.

### 2.3 Test Planner

* **Role**: Converts metadata into a test manifest.
* **Function**: Parses code repo and test framework, determines which tests to run and required devices.
* **Example**: From commit `abc123`, generates a list of smoke tests for Android using Behave.

### 2.4 Test Dispatcher

* **Role**: Orchestrates test scheduling and sharding.
* **Function**: Queues test jobs based on device availability and manifest requirements.
* **Example**: Breaks 100 tests into 10 groups and schedules each on a matching device.

### 2.5 Executor Agent

* **Role**: Executes test jobs on devices.
* **Function**: Spins up a container, runs the test, captures results, and publishes logs.
* **Example**: Runs `test_login.feature` on Pixel 7, uploads logs to ELK, sends results to result queue.

### 2.6 Result Aggregator

* **Role**: Aggregates, stores, and forwards execution outcomes.
* **Function**: Collects test results from all agents, generates summary report.
* **Example**: 98 tests passed, 2 failed, uploads results to Xray and updates dashboard.

### 2.7 Notification Router

* **Role**: Routes alerts and reports.
* **Function**: Sends messages to Slack, email, or dashboards based on execution status.
* **Example**: Sends “Run Passed” to team Slack, sends failure traceback to on-call QA.

## 3. Service Interface Contracts

This section defines the formal **JSON-based contracts** used between services. These contracts ensure loose coupling and clear expectations for:

* Trigger events
* Test planning input/output
* Execution job dispatching
* Real-time status APIs
* Result and telemetry reporting

Each service in the pipeline must conform to these structures to maintain compatibility and observability.

### 3.1 Sample Status API Response (Service Interface Contracts)

This response represents the real-time status of an ongoing test plan execution. It allows systems such as dashboards, notification routers, or Jenkins monitors to track progress.

* `planId`: Unique identifier for the test plan
* `status`: Current lifecycle status (`Pending`, `Running`, `Completed`, `Failed`, etc.)
* `passed`: Count of passed tests so far
* `failed`: Count of failed tests so far

```json
{
  "planId": "test-run-12345",
  "status": "Running",
  "passed": 10,
  "failed": 2
}
```

### 3.2 Test Manifest Contract (Versioned Example)

This contract is generated by the Test Planner and defines the full execution blueprint. It includes:

* `manifestVersion`: Version of this contract schema (supports future extension)
* `planId`: Unique identifier for this test run plan
* `tests`: List of tests to execute, including priority and estimated duration
* `app`: Mobile app artifact details (path and version)
* `devices`: Required device types or specific serials (primary, secondary, optional groups)
* `execution_options`: Configuration flags (parallelism, retries, timeouts)
* `framework`: The BDD/test framework used (e.g. Behave, Espresso, XCTest)
* `metadata`: CI/CD and commit metadata (e.g. initiator, SHA, timestamps)

```json
{
  "manifestVersion": 2,
  "planId": "test-run-12345",
  "tests": [
    {
      "id": "TC_001",
      "name": "LoginTest",
      "priority": "High",
      "estimatedDurationSec": 30
    }
  ],
  "app": {
    "path": "artifactory/releases/calendar-v1.3/calendar-v1.3.apk",
    "version": "v1.3"
  },
  "devices": {
    "primary": [
      {"model": "Pixel 7", "os": "13", "serial": "emulator-5554"}
    ]
  },
  "execution_options": {
    "parallel_execution": true,
    "retry_failed": 1,
    "fail_fast": false,
    "timeout_minutes": 60
  },
  "framework": "behave",
  "metadata": {
    "initiated_by": "qa.lead@company.com",
    "commit_sha": "a1b2c3d4e5f67890abcdef1234567890",
    "created_at": "2025-07-18T10:33:15Z"
  }
}
```

### 3.3 Execution Request Contract (to Executor Agent)

This message is dispatched to an Executor Agent for a specific test shard. It includes:

* `planId`: ID of the test run
* `jobId`: Unique job identifier per test/device
* `test`: File and line/selector (for pinpointed execution)
* `device`: Target device spec (model, OS, serial)
* `appPath`: Resolved path to the APK or IPA
* `envVars`: Environment variables for the test context
* `timeout`: Max duration for this test case

```json
{
  "planId": "test-run-12345",
  "jobId": "job-456",
  "test": "features/login.feature:10",
  "device": {
    "model": "Pixel 7",
    "os": "13",
    "serial": "emulator-5554"
  },
  "appPath": "artifactory/releases/calendar-v1.3/calendar-v1.3.apk",
  "envVars": {
    "ENV": "staging"
  },
  "timeout": 180
}
```

### 3.4 Execution Result Message Contract

This message is published by Executor Agent upon test completion. It enables real-time result aggregation.

* `planId`, `jobId`, `test`: Identify the exact test case
* `status`: Result status (`PASSED`, `FAILED`, `SKIPPED`, etc.)
* `duration`: Runtime in seconds
* `device`: Metadata for the executing device
* `logs`: Execution logs and evidence (stdout, screenshots, traces)
* `timestamp`: UTC timestamp of result

```json
{
  "planId": "test-run-12345",
  "jobId": "job-456",
  "test": "features/login.feature:10",
  "status": "PASSED",
  "duration": 45,
  "device": {
    "serial": "emulator-5554",
    "model": "Pixel 7",
    "os": "13"
  },
  "logs": {
    "stdout": "Login test passed",
    "screenshotUrl": "http://storage.local/screenshots/job-456.png"
  },
  "timestamp": "2025-07-18T10:35:00Z"
}
```

### 4. Comparison: RabbitMQ vs. Kafka

This section explores the trade-offs between two popular message brokers: **RabbitMQ** and **Apache Kafka**. The chosen broker underpins the message-driven architecture and has major implications for latency, throughput, durability, and observability.

#### 4.1 Architectural Role in the System

* The message broker is the **backbone of inter-service communication**.
* It enables decoupling between:

  * Trigger components and Test Planner
  * Dispatcher and Executor agents
  * Executor results and Aggregator

#### 4.2 Message Types Handled

| Stage                      | Event Topic / Queue | Broker Responsibilities                   |
| -------------------------- | ------------------- | ----------------------------------------- |
| Trigger Listener           | `trigger.events`    | Ensures test requests are queued reliably |
| Test Planner to Dispatcher | `test.plan`         | Transmits test manifests to scheduler     |
| Dispatcher to Executor     | `test.jobs.*`       | Routes test shards to agents              |
| Execution Feedback         | `test.results`      | Streams results for aggregation           |
| Notifications              | `alerts.status`     | Routes status updates and failures        |

#### 4.3 Broker Feature Comparison

| Feature             | RabbitMQ                          | Kafka                          |
| ------------------- | --------------------------------- | ------------------------------ |
| Delivery model      | Push                              | Pull                           |
| Message ordering    | Per queue                         | Per partition                  |
| Message durability  | Optional, queue-level persistence | Default, log-based persistence |
| Routing flexibility | High (exchanges, bindings)        | Low (basic topic structure)    |
| Replay support      | No (manual requeueing)            | Yes (offset-based)             |
| Throughput          | Moderate                          | High                           |
| Latency             | Low                               | Slightly higher                |
| Fan-out support     | With multiple queues/bindings     | Built-in via consumer groups   |
| Operations          | Easier to operate                 | Requires more tuning           |

#### 4.4 Recommendations

* **RabbitMQ** is better suited if your team prioritizes:

  * Real-time task dispatching with low latency
  * Simpler operational overhead
  * Fine-grained routing logic

* **Kafka** is ideal if your system must:

  * Scale to extremely high throughput
  * Retain message history for replay/debugging
  * Handle large analytics or streaming pipelines

In most test orchestration environments with moderate volume and a strong routing requirement, **RabbitMQ** is the recommended starting point.

| Feature             | RabbitMQ                          | Kafka                          |
| ------------------- | --------------------------------- | ------------------------------ |
| Delivery model      | Push                              | Pull                           |
| Message ordering    | Per queue                         | Per partition                  |
| Message durability  | Optional, queue-level persistence | Default, log-based persistence |
| Routing flexibility | High (exchanges, bindings)        | Low (basic topic structure)    |
| Replay support      | No (manual requeueing)            | Yes (offset-based)             |
| Use case fit        | Task queues, workflows            | Event streaming, analytics     |
| Ops complexity      | Lower                             | Higher                         |
| Fan-out support     | With multiple queues/bindings     | Built-in via consumer groups   |

### 5. Comparison: Docker vs. Bare Metal Execution

This section compares Docker containerization with traditional bare metal execution for running mobile automation test agents.

#### 5.1 Execution Environment Considerations

* The Executor Agent is responsible for running test jobs on-demand. Choosing the right environment impacts:

  * Test isolation
  * Device connection
  * Resource allocation
  * Reproducibility and cleanup

#### 5.2 Use Case Profiles

| Environment    | Ideal Use Case                                                          |
| -------------- | ----------------------------------------------------------------------- |
| **Docker**     | Cloud/on-prem orchestration at scale, frequent test environment resets  |
| **Bare Metal** | Tests requiring access to hardware peripherals (e.g. USB, ADB over OTG) |

#### 5.3 Operational Trade-Offs

| Feature               | Docker Containers               | Bare Metal Execution         |
| --------------------- | ------------------------------- | ---------------------------- |
| **Isolation**         | Strong (namespaces, cgroups)    | Weak (global environment)    |
| **Provisioning Time** | Fast (container pull and start) | Slower (requires full setup) |
| **Environment Drift** | Low (immutable image)           | High (risk of config skew)   |
| **Parallelization**   | Easy with Kubernetes            | Limited by physical capacity |
| **Cleanup Overhead**  | Minimal (ephemeral containers)  | High (manual teardown risk)  |
| **USB Device Access** | Requires explicit mapping       | Native access                |
| **Security Risk**     | Lower with sandboxing           | Higher with shared userspace |
| **Maintenance**       | Simple with CI image builds     | Manual updates and patching  |

#### 5.4 Recommendations

* **Start with Docker** for most scalable and portable testing pipelines.
* For niche device interaction (e.g., USB accessories, Bluetooth HCI), use **dedicated bare-metal runners** integrated into the execution layer.
* Build hybrid support to allow a fallback to bare-metal when required, orchestrated by tagging test jobs in the manifest.

| Feature                 | Docker Containers                      | Bare Metal Execution             |
| ----------------------- | -------------------------------------- | -------------------------------- |
| Isolation               | Strong (per-container)                 | Weaker (shared host environment) |
| Setup time              | Fast (immutable images)                | Slower (manual/configured)       |
| Cleanup                 | Easy (stateless containers)            | Risk of state leaks              |
| Environment consistency | High (image-controlled)                | Varies by host state             |
| Scaling                 | Easy (via Kubernetes, HPA)             | Manual or static scaling         |
| Resource overhead       | Low                                    | Minimal                          |
| Hardware access         | Needs config (e.g., USB, GPU passthru) | Native                           |
| Use case fit            | CI/CD, scalable testing                | Specialized hardware scenarios   |

### 6. Kubernetes Orchestration and Hardware Lab Integration

#### 6.1 Kubernetes Role in the Architecture

* Kubernetes (K8s) is the core **container orchestration platform** used to manage lifecycle, scaling, and isolation of system components and test runners.
* It ensures each test execution is:

  * Run in an **ephemeral container**
  * Scheduled according to node/device affinity
  * Automatically cleaned up post-execution

#### 6.2 Kubernetes Features Leveraged

| Feature                       | Purpose                                      |
| ----------------------------- | -------------------------------------------- |
| **Namespaces**                | Environment isolation (dev, staging, prod)   |
| **Horizontal Pod Autoscaler** | Scales planner/dispatcher based on test load |
| **Node Selectors / Taints**   | Route jobs to nodes with connected devices   |
| **Secrets & ConfigMaps**      | Secure framework and device configurations   |
| **Persistent Volumes**        | Store execution logs and artifacts           |
| **Pod Disruption Budgets**    | Protect test runs from unexpected restarts   |

#### 6.3 Hardware Lab Integration

* The test system can be connected to a **hardware device lab** via:

  * USB-over-IP solutions (e.g., [usbip](https://github.com/torvalds/linux/tree/master/drivers/usb/usbip))
  * Physical host nodes with USB-connected devices (e.g., Android/iOS phones)
  * Device farm APIs (e.g., OpenSTF, HeadSpin, BrowserStack\*)

| Integration Mode       | Description                                     |
| ---------------------- | ----------------------------------------------- |
| **Direct USB Host**    | Kubernetes nodes physically attached to devices |
| **USB-over-IP**        | Redirect USB traffic to remote test agents      |
| **Remote Device Farm** | Use REST APIs to acquire/release remote devices |

> \*Remote cloud-based device providers require firewall and policy configuration and may not be suitable for full on-prem deployments.

#### 6.4 Scheduling Considerations

* Each test job must declare device affinity using Kubernetes `nodeSelector`, `labels`, or `topologySpreadConstraints`
* Pods that require device access are scheduled only on nodes with:

  * Matching physical connection
  * Available resource limits
  * Label-based device type compatibility (e.g., `android=true`, `pixel7=true`)

### 7. Example Scenario – Jenkins Trigger Flow

#### 🎯 Use Case:

A QA lead triggers a @smoke test suite on the release/v1.3 branch using Jenkins. They target two device types and request fast failure on error.

#### 🧭 Step-by-Step Flow Through Architecture Components

**1. Trigger Initiation via Jenkins UI**

* Git branch: `release/v1.3`
* App artifact: `calendar-v1.3.apk`
* Test tags: `@smoke`, `@login`
* Device filters: `Pixel 7 + Samsung S21`, OS `13–14`
* Execution options: `fail_fast = true`, `retry_failed = 2`, `timeout = 45`

Jenkins generates the following execution contract JSON and sends it to the Trigger Listener:

```json
{
  "version": "1.0",
  "trigger_metadata": {
    "source": "jenkins",
    "initiated_by": "qa.lead@company.com",
    "requested_at": "2025-07-18T10:33:00Z",
    "source_job_id": "Run-Mobile-Automation-#201",
    "tracking_id": "abc123-def456",
    "priority": "high"
  },
  "simulate": false,
  "source": {
    "type": "existing_artifacts",
    "artifact_path": "artifactory/releases/calendar-v1.3/",
    "artifacts": ["calendar-v1.3.apk"]
  },
  "test_sources": {
    "test_source_1": {
      "type": "git_branch",
      "branches": ["main"],
      "repository": "https://git.company.com/mobile-tests.git"
    }
  },
  "test_selection": {
    "test_tags": ["@smoke", "@login"]
  },
  "device_roles": {
    "primary": {
      "models": ["Pixel 7", "Samsung Galaxy S21"],
      "os_versions": ["13", "14"],
      "labels": ["project:calendar"]
    }
  },
  "execution_options": {
    "parallel_execution": true,
    "retry_failed": 2,
    "fail_fast": true,
    "timeout_minutes": 45
  }
}
```

**2. Trigger Listener**

* Accepts the JSON payload
* Performs schema validation
* Adds headers and places the message on the queue

**3. Trigger Router**

* Validates values (e.g. tag syntax, timeout)
* Fetches commit SHA from Git
* Confirms artifact availability
* Adds enrichment:

```json
{
  "commit_sha": "a1b2c3d4e5f",
  "env": "staging",
  "build_id": "#201",
  "expanded_tags": ["test_login.feature", "test_checkout.feature"]
}
```

**4. Test Planner**

* Clones the repo at commit `a1b2c3d4e5f`
* Resolves tag-to-feature mappings
* Confirms test/device compatibility
* Constructs final execution manifest:

```json
{
  "manifest": {
    "tests": [
      "features/login.feature:10",
      "features/checkout.feature:22"
    ],
    "app": {
      "path": "artifactory/releases/calendar-v1.3/calendar-v1.3.apk",
      "version": "v1.3"
    },
    "devices": {
      "primary": [
        {"model": "Pixel 7", "os": "13"},
        {"model": "Samsung Galaxy S21", "os": "14"}
      ]
    },
    "execution_options": {
      "fail_fast": true,
      "retry_failed": 2,
      "timeout_minutes": 45
    }
  }
}
```

#### ✅ Component Summary Table (Jenkins Trigger Path)

| Component        | Reads                             | Validates/Transforms                          | Emits / Forwards                |
| ---------------- | --------------------------------- | --------------------------------------------- | ------------------------------- |
| Trigger Listener | Full JSON schema from Jenkins UI  | Schema conformity, safe headers               | → Message Queue                 |
| Trigger Router   | Base payload + repo/artifact info | Enriches with commit, build, expanded tags    | → Test Planner                  |
| Test Planner     | Enriched payload                  | Converts to manifest: test list, devices, app | → Test Dispatcher / Coordinator |

### Final Summary

The Mobile Automation Testing System is designed as a robust, modular, and scalable solution for orchestrating mobile test executions. It leverages asynchronous microservice communication via RabbitMQ or Kafka, containerized services managed by Kubernetes, and strict interface contracts for traceability and reliability.

Key strengths include:

* **Standardized trigger flow** from Jenkins, Bitbucket, or Xray through a unified interface
* **Resilient execution pipeline** with fault tolerance, retries, and watchdogs
* **Flexible device orchestration** and test sharding via manifest-driven execution
* **Clear message schemas and APIs** ensuring service independence and ease of maintenance
* **Comprehensive observability and reporting** with telemetry, ELK integration, and notification routing

With a focus on on-premises deployment and extensibility, this architecture ensures high operational efficiency and supports both current QA workflows and future scaling requirements.
